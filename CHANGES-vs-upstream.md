# What we changed vs upstream Blender v4.5.13, and why

The source delta is small (8 files, ~60 lines; see `PATCHES/`). Each fix corresponds to a concrete
wall hit when building Blender with CUDA-Cycles + OIDN + OSL on Jetson Thor (Blackwell sm_110,
JetPack 7, CUDA 13, Ubuntu 24.04 aarch64). The Cycles CUDA arch selection is **not** a source patch;
it is a configure flag (`-DCYCLES_CUDA_BINARIES_ARCH=sm_110;compute_90`) set by `recipe/20-blender.sh`.

## 0001 - deps/sqlite: autoreconf -fi before ./configure
sqlite's bundled configure was generated by an older libtool. On Ubuntu 24.04 aarch64
(libtool 2.4.6/2.4.7 split) it fails; regenerating the autotools files first fixes it.

## 0002 - deps/libglu: autoreconf -fi before ./configure
Same libtool-split issue as sqlite, for libGLU.

## 0003 - deps/cython: tolerate setuptools 63.2.0 install_egg_info crash (|| true)
setuptools 63.2.0 crashes in `install_egg_info` AFTER Cython's files are already installed and numpy
has built. Appending `|| true` lets the deps build continue past the harmless post-install crash.

## 0004 - deps/wayland: harvest wayland/lib (aarch64) not wayland/lib64
On aarch64 the wayland dependency installs into `lib/`, not `lib64/`; fix the harvest path so the
files are actually collected into the harvest target.

## 0005 - deps/osl: do not force OSL_USE_OPTIX=ON on ARM (CPU-only OSL)
Upstream forces OSL's OptiX path on. That path compiles OSL shadeops to PTX via clang
(LLVM_COMPILE_CUDA), which breaks on CUDA 13 + clang 17 in `texture_fetch_functions.h`. It is also
pointless on Jetson: there is no OptiX runtime and Blender is built `WITH_CYCLES_DEVICE_OPTIX=OFF`,
so Cycles runs OSL on the CPU regardless. Leaving `OSL_USE_OPTIX=OFF` means `find_package(CUDA)`
never runs and the CUDA_FOUND-gated GPU-shadeops block is skipped; only the CPU LLVM-bitcode path
builds. Result: working CPU OSL (GPU-OSL is not available on Jetson, which is expected, not a gap).

## 0006 - deps/oidn: enable CUDA GPU device on sm_110 via RuntimeStatic (CUDA 13)  [the important one]
Enables GPU-accelerated OpenImageDenoise: `-DOIDN_DEVICE_CUDA=ON` and, crucially,
`-DOIDN_DEVICE_CUDA_API=RuntimeStatic`.

Why RuntimeStatic is non-obvious and mandatory: OIDN's default `Driver` backend (`curtn.cpp` shim)
does not provide `__cudaLaunchKernel` - the internal symbol CUDA 13's nvcc lowers `<<<>>>` kernel
launches to. So `device_cuda.so` builds fine but fails to dlopen at runtime with
`undefined symbol: __cudaLaunchKernel`, and OIDN SILENTLY falls back to the CPU denoiser (no error).
`RuntimeStatic` links the real `libcudart_static.a`, which has the symbol - self-contained, loads.

Plus sed patches to OIDN's `devices/cuda` build: drop `compute_70` (nvcc 13 rejects Volta), add
native `sm_110`, retarget the never-used sm70 CUTLASS translation unit to `sm_75`, and widen the
device `isSupported()` check from 109 to 119 so SM 11.0 is accepted.

DEBUGGING TRAP for anyone extending this: an OIDN build that SUCCEEDS and harvests `device_cuda.so`
does NOT mean GPU denoise works - the dlopen failure is silent. Verify at runtime with
`OIDN_VERBOSE=2` (look for `Type: CUDA`) and `LD_DEBUG=libs`. See `verify/oidn_cuda_test.c` and
`verify/cycles_oidn_gpu_test.py`.

## 0007 - deps: re-enable cmake/osl.cmake include (CPU-only OSL); keep mesa/weston off
Re-enable the OSL dependency include (built CPU-only per 0005). `mesa` and `wayland_weston` stay
commented out: leaf packages, aarch64-broken, and unnecessary - Blender uses the system GL and runs
either headless (EGL offscreen) or on the system GNOME/X11 session.

## 0008 - blender: link libdrm for our DRM/kmsgrab-enabled deps-ffmpeg
The deps-built ffmpeg is compiled with DRM/kmsgrab support, which leaves undefined `drm*` references
at Blender's final link. Append `drm` to `FFMPEG_LIBRARIES` after `find_package(FFmpeg)` (and
`apt install libdrm-dev`). Also note (in-tree, not a code change): `-DLIBDIR` must be passed
explicitly at configure time because this file only auto-detects the libdir when it carries a `.git`
submodule marker, which a harvested `lib/` tree does not have.

## Not a patch, but part of the recipe
- **Cycles CUDA arch** = `sm_110;compute_90` (configure flag). Native sm_110 cubin removes the
  ~371s one-time first-render PTX->SASS JIT; compute_90 PTX is retained as a portable sm_90+ fallback.
  sm_110 needs no CMake change: it falls through the arch gate in
  `intern/cycles/kernel/CMakeLists.txt` to the default branch, which uses CUDA 13's nvcc directly.
- **Git-LFS**: point `lfs.url` at projects.blender.org (GitHub mirror 404s on LFS objects) and
  `git lfs pull` both `release/datafiles/**` (required; else runtime segfault on pointer stubs) and
  `assets/**` (bundled brushes / geometry-node assets; else "Unrecognized file format").
